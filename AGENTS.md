# fasthep-cli Agent Instructions

These instructions apply when working in the standalone `fasthep-cli`
repository. The Python package is `fasthep_cli`; the console script is
`fasthep`.

## Ownership

`fasthep-cli` owns the user-facing command line:

- command routing through the Typer app in `src/fasthep_cli/app.py`;
- command names, options, arguments and help text;
- exit behaviour and error conversion;
- stdout/stderr formatting, quiet/logo behaviour and machine-readable output;
- dispatch to FAST-HEP package APIs and shared helper utilities.

It intentionally contains little domain logic. CLI handlers should parse
arguments, call public APIs, format the result and return the right exit code.

## Package Boundaries

- `fasthep-flow` owns workflow normalisation, compilation, plan diffs, runtime
  execution and provenance APIs. CLI workflow commands should call `hepflow.api`
  or other public Flow APIs, not compiler/runtime internals.
- `fasthep-curator` owns schema inspection and diagnostics. `fasthep inspect`
  should delegate through Curator public APIs.
- `fasthep-render` owns rendering. `fasthep render` should delegate through
  Render public APIs and handle optional-package absence clearly.
- `fasthep-toolbench` owns shared console/display, package discovery, downloads,
  tool discovery, installation and execution helpers. Keep those helpers there
  rather than duplicating them in CLI command modules.
- `fasthep-carpenter` and experiment analysis packages own analysis operations
  and workflow semantics. Do not import companion-package internals to implement
  CLI behaviour.

## Command Surface

- Top-level app and `version`, `versions`, `download`:
  `src/fasthep_cli/app.py`
- Workflow commands: `commands/normalise.py`, `commands/make_plan.py`,
  `commands/compile.py`, `commands/run.py`, `commands/run_plan.py`,
  `commands/diff.py`
- Project setup: `commands/init.py`
- Inspection: `commands/inspect.py`
- Rendering: `commands/render.py`
- Provenance: `commands/provenance.py`
- External tools and DAS discovery: `commands/tools.py`
- Shared CLI helpers: `partition.py`, `progress.py`, `testing.py`, `logo.py`
- Tests: `tests/test_cli_*.py` plus `tests/_helpers.py`
- Documentation source: none currently exists; `pixi.toml` still defines a
  `docs` task for a future `docs/` tree.

## Development Commands

Use Pixi from the repository root.

- Install/update the development environment: `pixi install`
- Format: `pixi run format`
- Lint: `pixi run lint`
- Autofix lint: `pixi run lint-fix`
- Type-check: `pixi run typecheck`
- Test: `pixi run test`
- Package build: `pixi run build`
- Build docs, once `docs/` exists: `pixi run docs`
- Clean built docs: `pixi run docs-clean`
- Standard validation: `pixi run check`
- Release-style validation: `pixi run ci`
- Distribution check after building: `pixi run check-dist`

`check` runs lint, type-check and tests. `ci` runs `check` and then builds the
package. Pixi environments include `py311`, `py313`, `py314` and `docs`; use
environment-qualified runs for Python-version or docs-specific work.

## CLI Compatibility

- Preserve stable command names, aliases, option names, argument order, exit
  codes, stdout/stderr split and parseable output such as `versions --display
  json` and `tools run --json`.
- Error messages are user-facing diagnostics. Keep them actionable and avoid
  exposing implementation stack traces for expected user mistakes.
- Optional capabilities should fail clearly when unavailable. Test optional
  package absence and capability discovery where relevant.
- Avoid requiring network access, batch infrastructure, global tool installs or
  large datasets in routine CLI tests. Use mocks, temporary files and small ROOT
  fixtures.

## Testing Expectations

- Split tests by command or feature, following `tests/test_cli_compile.py`,
  `tests/test_cli_run.py`, `tests/test_cli_inspect.py`, etc. Do not grow a
  single monolithic CLI test module.
- Individual command changes should test argument parsing, delegated API call
  shape, stdout/stderr, exit code and generated paths.
- End-to-end CLI behaviour should use `typer.testing.CliRunner` through
  `tests/_helpers.py`, with `FASTHEP_NO_LOGO=1` where output assertions need to
  be stable.
- Workflow command tests should use tiny synthetic workflows and plans. They
  should not require real experiment datasets or remote storage.
- Tools command tests should cover missing-tool handling, auto-install/no-install
  flags, `CommandResult` exit-code propagation and JSON output.
- Keep guards that prevent importing Flow compiler/runtime internals or
  reimplementing package-owned dispatch helpers.

## Generated Files

- Do not edit `src/fasthep_cli/_version.py` by hand; it is generated by
  `hatch-vcs`. Keep `src/fasthep_cli/_version.pyi` aligned if public typing
  changes.
- CLI test outputs, compiled workflow artifacts, downloaded files and generated
  docs are products of tests or commands. Do not check them in unless they are
  intentional fixtures.
